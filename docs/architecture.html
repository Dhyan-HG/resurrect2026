Sentinel

Data and system architecture · Resurrect 2026, Problem 2 (+ Problem 6) · github.com/roshanvijay37/resurrect2026 · live at chatu.in

In one sentence. Every fact Sentinel knows arrives as an event; events are stored once, never edited, and the whole picture of stock, orders and risk is rebuilt from them, so duplicates, junk or a replay can never change a number.
Honest scope. Built marks what runs today at chatu.in: an in-memory event store per visitor, rebuilt on every change. Production design marks how the same model maps to a database (Postgres) for a real plant. That part is a design, not built or measured.

1. The big picture

Events flow left to right. An approved purchase becomes a new event (a purchase order), which flows back into the store.

2. Events: the only way data gets in Built

Every event has the same envelope plus a few fields that depend on its type. Code: sentinel/events.py.

Limits that keep one bad sender from breaking the plant: quantities up to 10,000,000, event size up to 4 KB, text up to 2,000 characters; the latest 500 quarantined events are kept, with totals counted.

3. From events to the picture on screen Built

Rebuild (engine.rebuild)

Events are sorted by (ts, event_id) and replayed into a book: on-hand stock per material, every order and its status, every purchase order with its received quantity and date history, stock-count discrepancies and anomalies. Because the order is fixed, any replay gives the same book; a hash of it proves it.

Projection (engine.project)

Net availability = on hand + incoming − allocated. Open orders are served earliest customer date first; each takes stock, then incoming POs by their risk-adjusted arrival (the supplier's learned average delay is added). Production starts when every part is covered and takes 2 days, giving each order a projected ship date and a risk: late, at risk (< 2 days spare) or on track.

4. Production design: the same model in Postgres Production design

The event model maps directly to an append-only table; everything else is either master data or a cache that can be thrown away and rebuilt.

Arrows point to the table a row refers to. Approvals and questions also write an event, so the event log stays the single source of truth.

ConcernHow the design handles it
DuplicatesINSERT … ON CONFLICT (event_id) DO NOTHING; a conflicting copy goes to quarantine.
Malformed eventsValidated in the API before insert; failures land in quarantine with the reason.
SpeedRebuild from the latest book_snapshot plus newer events, not from day one. Index on (ts, event_id).
AuditNothing is updated in place: who approved what, and when, is an event.
RolesTaken from the company sign-in (SSO). In the demo the role is a page switch.
EmailAn approved draft goes to outbox; a worker sends it. Nothing is sent before approval.

5. The demo server today Built

PartWhat it is
RuntimePython 3.12, FastAPI + Uvicorn, one Docker container on our server (Caddy for HTTPS), deployed by GitHub Actions on every push.
SessionsEach visitor gets their own simulated plant (cookie), up to 24 at once, idle ones removed after 45 minutes; writes limited to 40 per 10 seconds.
Data sourceA seeded plant simulator (sentinel/world.py) sends events with deliberate faults: duplicates, junk, shuffled order, outages, vague supplier messages. External systems can post the same events to /api/events.
StorageIn memory. A restart starts every plant again from day 4. Results of the evaluation are files in results/.
